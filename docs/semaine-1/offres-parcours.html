Gesta · architecture applicative

Le parcours des offres

De la page React à la requête SQLite, voici comment une liste d’offres est demandée, filtrée selon le profil connecté, transformée en réponse API puis affichée.

Architecture en bref

Frontend

React et TypeScript, servis par Vite. La page assemble les composants et les hooks ; le hook appelle un service HTTP ; le service valide la réponse avant de l’exposer à l’interface.

Backend

API Express en TypeScript, organisée en contrôleurs, services métier, repositories SQL et mappers. SQLite est accédée par better-sqlite3.

Du composant React à la base de données

Pendant le développement, le navigateur demande /api/offers. Le proxy Vite enlève /api et transmet la requête à l’API (port 3000 par défaut).

  1. 1

    La page déclenche le chargement et choisit l’affichage

    OffersPage appelle le hook, puis affiche un état de chargement, une erreur, un état vide ou le nombre de résultats suivi du tableau.

    frontend/src/pages/OffersPage.tsx
    Composition

    App.tsx fournit le profil, le jeton et le callback de déconnexion à la page.

    Rendu

    OfferTable rend titre, entreprise, année, période et statut avec les libellés français.

    frontend/src/App.tsx frontend/src/components/OfferTable.tsx

  2. 2

    Le hook gère l’état asynchrone

    useOffers appelle le service, stocke les offres, l’erreur et l’état de chargement, puis annule une requête devenue obsolète. Une réponse 401 déclenche le callback de session expirée.

    frontend/src/hooks/useOffers.ts
  3. 3

    Le service appelle l’API et contrôle les données

    getOffers envoie le jeton directement dans l’en-tête Authorization. readJson vérifie le statut HTTP et isOfferList valide la forme du JSON reçu.

    frontend/src/services/offers.service.ts frontend/src/utils/api.ts frontend/src/utils/guards.ts

  4. 4

    Express authentifie et autorise

    app.ts assemble les dépendances et protège la route. Le middleware d’authentification vérifie le jeton et recharge l’utilisateur actif et ses rôles depuis la base. La route vérifie ensuite le droit de lister des offres.

    backend/src/app.ts backend/src/middlewares/authenticate.ts backend/src/middlewares/authorize.ts

  5. 5

    Le contrôleur délègue au service métier

    Le contrôleur obtient l’utilisateur authentifié, demande la liste au service et convertit chaque résultat en DTO de réponse.

    backend/src/controllers/offers.controller.ts

  6. 6

    Le service combine les règles de visibilité

    L’administrateur reçoit toutes les offres, l’étudiant uniquement les offres publiées, et le déposant uniquement celles qu’il a déposées. Un contact sans rôle déposant reçoit un refus d’accès.

    backend/src/services/offers.service.ts backend/src/services/permissions.ts

  7. 7

    Le repository exécute SQL sur SQLite

    Le repository joint les offres aux entreprises, années académiques et périodes. Il applique les critères de visibilité fournis et trie les résultats par année puis date de création.

    backend/src/repositories/offers.repository.ts

  8. 8

    Le résultat remonte et devient le DTO public

    Le mapper convertit les colonnes SQL en objet métier, puis l’objet métier en DTO limité aux champs nécessaires à la liste. Le service frontend vérifie le DTO ; la page transmet les offres au tableau.

    backend/src/mappers/offer.mapper.ts backend/src/models/offer.ts frontend/src/models/offer.ts

Fichiers concernés par un filtre par période

À noter : la période est déjà fournie par l’API, présente dans le modèle frontend et affichée dans le tableau. Le besoin nouveau porte sur le critère de recherche : il faut le faire passer de l’interface à la requête SQL, sans remplacer les restrictions de visibilité par profil.

Interface et requête
  • frontend/src/pages/OffersPage.tsx — conserver l’état de période sélectionnée et afficher les résultats filtrés.
  • frontend/src/components/OfferTable.tsx — ajouter le contrôle de sélection ici, ou extraire un composant de filtre ; le tableau est actuellement seulement présentational.
  • frontend/src/hooks/useOffers.ts — accepter la sélection et recharger/filtrer lors de sa modification.
  • frontend/src/services/offers.service.ts — transmettre la période comme paramètre de requête, par exemple ?period=P1.
  • frontend/src/utils/guards.ts et frontend/src/models/offer.ts — probablement inchangés pour un filtre seul : le code période et la validation des offres existent déjà. À revoir si l’API ou ses données changent.
API et persistance
  • backend/src/controllers/offers.controller.ts — lire et valider le paramètre de requête, puis le transmettre au service.
  • backend/src/services/offers.service.ts — combiner le filtre de période avec le filtre de visibilité propre au profil.
  • backend/src/repositories/offers.repository.ts — ajouter le critère SQL sur p.code (ou period_id) et passer la valeur liée en paramètre.
  • backend/API.md — documenter le paramètre, ses valeurs autorisées et les erreurs de validation.
  • backend/src/models/offer.ts — le type PeriodCode existe déjà (P1, P2, OTHER) ; l’étendre seulement si les valeurs métier changent.
Tests à adapter
  • backend/tests/offers.test.ts — tester les périodes retournées, les paramètres invalides et le maintien des règles de visibilité par profil.
  • frontend/tests/OffersPage.test.tsx — tester le contrôle et les offres affichées pour la période choisie.
  • frontend/tests/helpers/fetchMock.ts — utiliser le mock existant pour vérifier la requête/API simulée ; créer un test de service séparé seulement si cela suit les tests présents.
Données déjà disponibles
  • backend/src/db/migrations/001_initial.sql — définit les périodes et leur lien aux offres via period_id. Un filtre de lecture ne nécessite normalement pas une nouvelle migration.
  • backend/src/mappers/offer.mapper.ts — expose déjà le code de période dans le DTO de liste ; à modifier seulement si sa forme change.
  • frontend/src/utils/labels.ts — contient les libellés affichés (P1, P2, OTHER) ; réutiliser ces libellés pour le sélecteur.
  • docs/architecture.md — mettre à jour le parcours de référence si le nouveau contrôle devient une partie durable du flux.
Parcours décrit à partir de l’implémentation actuelle de Gesta. Le filtre par période est une piste d’évolution ; aucun code applicatif n’est modifié par ce document.
